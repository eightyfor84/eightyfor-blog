Welcome to **Chronicle Aurora** — the 3.1.x release of Chronicle, a local-first, git-backed Jamstack blog system. This post is your starting point: it explains what Chronicle is, how the four-layer architecture works, and how the example posts in this blog double as its documentation.

## The Core Philosophy

Chronicle is built on three principles:

1. **Local-first** — Everything lives on your filesystem as Markdown and YAML. There is no database, no API server, no runtime service. Your content is plain files you can read, diff, and back up with the tools you already use.
2. **No server** — The blog is generated by an Astro SSG build (`data/` → `dist/`) and edited in a local Electron CMS (the Manager). Nothing runs at request time; the output is pure static HTML you can host anywhere.
3. **Git is the API** — There is no sync endpoint to call. `git commit` saves a change, `git push` deploys it, `git pull` syncs it. Authentication is your SSH key; history, branching, and rollback come free.

Because there is no server, the three pieces of the system each do exactly one job: **build** = Astro SSG (`data/` → `dist/`), **edit** = the Electron Manager (reads and writes `data/` directly), **deploy** = git push → CI/CD → CDN.

## Four-Layer Architecture

Chronicle's frontend is built as a **lightweight core + pluggable features**. The core renders posts and pages and knows nothing about search, comments, collections, friends, or slides — those are *plugins* that register themselves.

```
┌──────────────────────────────────────────────────────────┐
│ Core (mainboard) — data contract + page skeleton         │
│ · Renders posts/pages; owns routing, layout, i18n        │
│ · Knows nothing about search/comments/collections/...    │
├──────────────────────────────────────────────────────────┤
│ Plugins — register via manifest                         │
│ · search / comments / reading-experience / friends       │
│   / collections / slides                                 │
│ · Each = pages + slots + data hooks + settings schema    │
├──────────────────────────────────────────────────────────┤
│ Theme — all styles live in the theme                     │
│ · tokens / global / critical CSS, component styles       │
├──────────────────────────────────────────────────────────┤
│ Manager — schema-driven CMS, adapts via template manifest│
└──────────────────────────────────────────────────────────┘
```

**This demo site ships with every plugin enabled** (search, comments, reading experience, friends, collections, slides) so you can see the full feature set. Flip any plugin off in `data/site.yml` (or the Manager's plugin page) and its pages, components, and styles leave the next build — nothing else changes. That is the point of the architecture: the core stays small, and every feature is optional.

## `data/` — The Single Source of Truth

All content and configuration lives under `data/`. There is no `site/` directory, no conversion step, no dual-source synchronization — `data/` is the only source of truth, read directly by both the Manager and the build.

Two rules keep the tree predictable:

- **YAML for humans, JSON for programs.** Configuration and content (`site.yml`, `profile.yml`, `friends.yml`, `collections.yml`, post frontmatter) are YAML — commented, hand-editable, clean git diffs. JSON is reserved for program-written files: `posts/index.json` (the derived post index) and `comments/{id}.json` (static comments).
- **The directory is the namespace.** No cryptic file prefixes. The folder tells you what a file is: `posts/<id>/index.md` is a post, `background/` holds the site background.

The key files:

```
data/
├── site.yml               # Site configuration (homepage, appearance, rss, analytics, post,
│                          #   plus one section per enabled plugin)
├── profile.yml            # Author profile
├── friends.yml            # Friends page (friends plugin)
├── collections.yml        # Collections (collections plugin)
├── background/            # Site background image + background.yml meta
├── avatar/                # Author avatar
├── posts/
│   ├── index.json         # Post index (auto-generated — never hand-edit)
│   └── <id>/index.md      # One directory per post: frontmatter + Markdown body
└── comments/{id}.json     # Approved comments (Staticman format)
```

`site.yml` is grouped **by plugin**: the core sections (homepage/appearance/rss/analytics/post) come first, then one section per plugin, each with its own `enabled` switch and configuration. Disabling a plugin means its section is ignored at build time — the feature's components and styles never enter the bundle.

## Directories Are Data Sources

Chronicle follows a "put it there, it works" model for media: instead of storing image paths in YAML, the canonical directory *is* the data.

- **`data/background/`** — drop any image here and it becomes the site background; the first image is used, multiple images are randomly picked. `background.yml` holds the meta (mode, position, size, blur, overlays).
- **`data/avatar/`** — any image here is the author avatar.
- **`data/posts/<id>/`** — a post is a directory named by its id (normally a readable slug), containing `index.md` and any post-specific attachments.

The CMS copies selected images into these directories, and the build compresses them to WebP/AVIF. Compression is a CI/CD concern, not an editor concern: `data/` stores source-quality images, and the build pipeline optimizes them universally.

## Quick Start

1. **Install the CMS** — install the Manager (Electron) and open it in your repository. It scans `data/`, discovers posts, and gives you schema-driven settings forms for every YAML file.
2. **Write a post** — click New Post, give it a title (the directory id is derived from it), and write in Markdown. Articles created outside the CMS are auto-discovered on startup.
3. **Deploy** — commit your changes and push. CI rebuilds the site (`data/` → `dist/`) and publishes static files to your CDN.

If you ever want to start over, **Settings → System → Reset** offers three levels — template settings, CMS configuration, or clearing `data/` entirely (a CLI script covers the same ground).

Everything you see on this blog is just files on disk. There is no magic behind the scenes — open `data/` and you hold the entire site in your hands.
